## Official endpoints used (Meta Threads API docs)

- Authorize URL: `https://threads.com/oauth/authorize` (unchanged from PB-P0-003; `response_type=code`, `scope` must include `threads_basic`; ONLY `threads_basic` is requested for this pilot — no publish/manage/reply scopes).
- Short-lived token: `POST https://graph.threads.net/oauth/access_token` (form-encoded; `client_id`, `client_secret`, `code`, `grant_type=authorization_code`, identical `redirect_uri`; secret ONLY in the POST body, never in any URL).
- Long-lived token: `GET https://graph.threads.net/access_token?grant_type=th_exchange_token&client_secret=...` (short-lived token via `Authorization: Bearer` header).
- Refresh: same endpoint with `grant_type=th_refresh_token`.
- Identity: `GET https://graph.threads.net/v1.0/me?fields=id,username` (token via `Authorization: Bearer` only).

## Security decisions (fail-closed)

1. Granted scopes: Meta documents NO Threads endpoint that enumerates granted scopes for a user token. `getGrantedScopes()` therefore ALWAYS returns `{ verified: false, scopes: [] }`. Requested config scopes are NEVER reported as granted; all scope-dependent actions stay disabled until an authoritative verification channel is identified and verified.
2. Graph host is fixed/allowlisted (`https://graph.threads.net`); any non-allowlisted origin is refused before the transport runs.
3. Redirects are never followed (`redirect: 'manual'`); a 3xx from token endpoints fails closed.
4. Per-request timeout (`AbortSignal.timeout`, 10s) and a 64 KiB response body cap.
5. Provider errors are sanitized: error envelopes are mapped to coarse kinds only; provider message bodies, tokens, codes and secrets never appear in thrown errors or logs.
6. Response JSON is strictly shape-validated (object with required typed fields); malformed JSON, arrays, or missing fields fail closed as `unknown`.
7. Token code 190 maps to `token_expired`; other envelopes to `unknown`; HTTP 400/401 to `invalid_code`, 403 to `permission_denied`, 5xx to `provider_unavailable`.

## Staging env key names (values never committed)

- `THREADS_APP_ID`, `THREADS_APP_SECRET`, `THREADS_REDIRECT_URI`, `THREADS_SCOPES=threads_basic`
- `PUBLIC_BASE_URL` (https origin the login link points at; redirect URI must sit under it in production)
- `DATABASE_URL`, `DATABASE_SSL_MODE=verify-full`, `DATABASE_SSL_CA_PATH` (hosted PG)
- `TOKEN_ENCRYPTION_KEY` (base64 of 32 bytes), `TOKEN_ENCRYPTION_KEY_ID`
- `APP_SIGNING_SECRET` (>=32 chars, server-only HMAC secret)
- `APP_HOST` (optional; default `127.0.0.1` loopback behind the reverse proxy), `PORT`

## First operator setup (safe procedure)

1. Owner confirms the operator's Telegram user id out-of-band.
2. A maintainer with approved DB access inserts exactly one row into `postbro.operators` (`status='active'`) via a reviewed, one-off SQL statement — never via this CLI or any unauthenticated path.
3. Operator minting is verified: `node dist/src/modules/auth/login-link-cli.js --operator <id>` refuses unknown/inactive ids (tested).
4. The CLI prints a single one-time link; deliver it over a private channel only. It expires in 5 minutes and is consumed atomically on first use.

## CLI usage (manual, operator-run only)

```
node dist/src/modules/auth/login-link-cli.js --operator <positive integer id>
```

Requires `DATABASE_URL` (+ TLS vars), `APP_SIGNING_SECRET`, `PUBLIC_BASE_URL`. Prints the one-time link on stdout and jti/expiry on stderr. Exit codes: 64 usage, 78 missing config, 1 operational failure. Not invoked by tests, CI, or agents.
