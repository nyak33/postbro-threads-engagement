## 1. Goal

Implement a secure, mock-first Threads OAuth account-connection flow in the PostBro Fastify backend:

1. An authorized Telegram-authenticated operator initiates "Connect Threads".
2. PostBro issues a short-lived, single-use, cryptographically random OAuth `state` bound to that operator and persisted hashed in `postbro.oauth_sessions`.
3. PostBro builds the exact Meta Authorization Window URL and redirects the operator's browser.
4. The HTTPS callback verifies state (valid, unexpired, unconsumed, bound to the initiating session) and exchanges the authorization code server-side.
5. PostBro exchanges the short-lived token for a long-lived token, retrieves the immutable Threads user ID and granted scopes, encrypts tokens at rest, and binds the account to the operator (`postbro.operator_accounts`).
6. A refresh path renews long-lived tokens before expiry; disconnect/reconnect and revoked-token handling fail safe.

Everything behind a **mockable provider client interface** so the full state machine is testable without Meta credentials or network access.

## 3. Scope

### In scope

- Config parsing/validation additions for the OAuth module (fail-fast on missing/invalid values when the module is enabled; see section 6).
- Token encryption helper (AEAD, e.g. AES-256-GCM with `TOKEN_ENCRYPTION_KEY`, key id stored in `token_key_id`) with explicit no-plaintext logging guarantees. If a suitable primitive already exists in the repo, reuse it; otherwise implement the smallest correct wrapper around Node `crypto`.
- `ThreadsOAuthClient` provider interface (ports/adapters): `buildAuthorizeUrl`, `exchangeCode`, `exchangeLongLived`, `refreshLongLived`, `getMe`/`getGrantedScopes`. A mock implementation for tests; a thin HTTP implementation wired to the documented endpoints. No third-party OAuth framework unless proposed in the PR.
- Routes (minimal, no dashboard):
  - `GET /auth/threads/start` — requires an operator-bound, signed link token (see below); creates `oauth_sessions` row (stores `state_hash` only), redirects to Meta Authorization Window.
  - `GET /auth/threads/callback` — validates `state`/`code`/error params; consumes session atomically; runs code exchange -> long-lived exchange -> identity/scopes -> encrypted persistence -> operator-account binding; renders a minimal success/failure page (no tokens).
- Signed operator link: the Telegram bot (PB-P0-004, not this task) will ultimately mint links. For this task, the start endpoint accepts an HMAC-signed link token (`APP_SIGNING_SECRET`) carrying `operator_id` + expiry; a tiny CLI/test helper mints tokens for tests. Fail closed on unknown/disabled operator.
- Token refresh service function (callable by a future worker; invoked manually in tests) with safe handling of expired/revoked tokens: mark account status `revoked`/needs-reconnect, never silently reuse a dead token.
- Disconnect/reconnect: disconnect clears ciphertext and marks status; reconnect reuses the OAuth flow and must update the SAME `threads_accounts` row matched by immutable `provider_id` (never create a duplicate account row for the same provider ID).
- Deterministic tests (section 5).

### Out of scope (do not implement)

- Telegram bot itself, menus, or approval cards (PB-P0-004).
- Persona binding enforcement beyond recording the operator-account link (PB-P0-005).
- Any reply send, sync, insights, discovery, DM, or other live Threads API feature.
- Hosted Supabase migration/writes; deployment, TLS, DNS; web dashboard.
- Legacy Postiz OAuth code import (license review required first; default: do not import).

## 4. Security and design requirements

1. `state`: >=128 bits from `crypto.randomBytes`, stored ONLY as SHA-256 hash (`state_hash`, matches existing 32-byte check), single-use (`consumed_at` set atomically in the same transaction as the check), default TTL 10 minutes, bound to `operator_id` and `purpose='threads_connect'`.
2. Callback rejects: unknown state, expired state, already-consumed state (replay), state whose operator no longer exists/is disabled, missing/invalid `code`, Meta `error=access_denied` (clean, non- scary user message), and provider exchange failures. All rejections leave no token material behind.
3. Redirect URI exactness: build authorize URL and code exchange from the SAME configured `THREADS_REDIRECT_URI`; validate at startup that it is an absolute HTTPS URL under `PUBLIC_BASE_URL` in production.
4. Tokens: encrypted before persistence; plaintext held in memory only for the duration of the exchange; never logged, never returned in any HTTP/Telegram response, never stored in audit rows. Refresh uses decrypted token server-side only.
5. Immutable identity: `threads_accounts.provider_id` is the Meta `user_id` from the token exchange / `me` response (confirm they match; mismatch = hard failure). Username is display-only metadata, never a key.
6. Cross-account isolation: every new query/helper takes explicit `account_id`/`operator_id`; RLS context set as in PB-P0-002 foundation; tests must prove operator A cannot see or act on operator B's accounts/sessions.
7. Granted scopes recorded verbatim per account; feature gating later compares against stored scopes, not assumed grants.
8. Error handling: map provider error bodies to a small internal enum (invalid_code, provider_unavailable, token_expired, revoked, permission_denied, unknown); safe user-facing text; full detail only in server logs with redaction.
9. Idempotency: concurrent callback requests with the same state resolve to exactly one consumed session and one account binding; duplicate `operator_accounts` rows impossible (PK already enforces).
10. No secrets in code/tests/git; tests use fixed dummy values clearly marked non-real.
