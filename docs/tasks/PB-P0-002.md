## 1. Objective and explicit boundary

Design and implement a reproducible **database foundation**, using Supabase-compatible PostgreSQL and strict TypeScript application access boundaries, on which P0 OAuth/persona binding and later P1 inbound engagement approvals/execution can safely build. Establish data isolation, account/operator authorization, basic encrypted-credential persistence interface, durable claim/idempotency primitives and audit records **without sending to Meta or creating a production database**.

PostBro is engagement-only and covers Threads **engagement automation**. Postiz owns posting/scheduling and is not a runtime dependency. Hermes development bot/LLM and PostBro product bot/runtime/credentials must remain separate.

**Implementation may proceed and pass all local acceptance tests without any hosted Supabase project, Supabase management access, production credentials, Meta app or product Telegram bot.** Real hosted-project verification remains separately gated. Do not claim S-04 cloud provisioning is complete from local tests.

## 3. In-scope deliverables

1. **Versioned, additive SQL migrations** that can build the scoped foundation cleanly and reproducibly on a disposable DB. Include indexes, uniqueness, check constraints, foreign keys and default timestamps.
2. **Core data access adapter** in TypeScript: typed DB client or query layer with parameterized SQL, bounded connections, explicit close, redacted errors, safe configuration that loads secrets only when DB operations are invoked. `GET /health` must still run without a DB URL or Supabase key; optional DB readiness must not report success when not connected.
3. **Account authorization boundary**: enforce operator → authorized Threads account → (where required) active persona binding in service code. Don't rely on Telegram caller-supplied account IDs. Every account-scoped read/write must be constrained by server-authorized account identity. Expose simple testable functions for a future OAuth/Telegram integration; don't invent external endpoints.
4. **Minimal transactional primitives** for safe one-time approval transitions and engagement-job claims/leases. Prefer database uniqueness and atomic statements (conditional update, transaction, `FOR UPDATE SKIP LOCKED` when appropriate), not in-memory flags.
5. **Audit/provenance hygiene**: no raw OAuth tokens, private keys or secrets in audit or exceptions. Time persisted in UTC with timezone-aware fields; posting schedule conversion belongs to Postiz.
6. **Automated database integration/security tests** using a reproducible disposable local database (ideally in CI); keep the existing 6 baseline tests passing and expand coverage. CI must fail if database migrations or isolation/concurrency tests fail. No tests depend on remote production services.
7. **Minimal documented runbook**: how to start/stop local DB, apply migrations to a clean DB, reset test fixtures, run tests and recover from migration failure. Document what is and is not proven by the test environment.

## 4. Data model — PRD Section 6 mapping

**Implement the first group now**, keeping names compatible with PRD or documenting a clear name map. Columns are design decisions subject to constraints below, not permission to expand features.

| Entity | Minimum purpose / constraints for this slice |
|---|---|
| `operators` | Unique immutable numeric Telegram user ID, active/disabled state; no public bot use implied. |
| `oauth_sessions` | Operator-bound hashed nonce/state, purpose, short expiry, consumed/replayed marker; no plaintext bearer values. |
| `threads_accounts` | Unique immutable Meta Threads provider ID (username is mutable), lifecycle status, scope/capability metadata, optional encrypted-token envelope + expiry (never plaintext). |
| `operator_accounts` (if join model selected) | Explicit access binding between operators and accounts; alternatively document/test an equally strict single-owner relation. |
| `personas`, `persona_versions`, `persona_bindings` | Account ownership, immutable version snapshots, one valid active binding per Threads account; FK/unique guarantees eliminate cross-account persona resolution. |
| `engagement_jobs` | UTC next retry/execution time, account/action scope, status (`pending`, `claimed`, `processing`, `confirmed`, `failed`, `needs_reconciliation` or a documented equivalent), lease/owner, attempts, non-reusable uniqueness key. |
| `engagement_events`, `engagement_proposals` | Stored only if needed to test approval/account relations; provider reply ID unique **per account** and proposal bound to account + event. No live sync or AI scoring. |
| `approvals` (and `edit_sessions` if necessary) | Operator, account, action ID, expiry, outcome; atomic approve/reject/expire, one-use callback; approved does NOT itself imply an external send. |
| `execution_attempts` | Account and action key, outcome including ambiguous/needs-reconciliation state; deterministic deduplication. No actual provider call. |
| `audit_events` | Operator/system actor, account, safe action label, reason, outcome, time and correlation ID; **never tokens or raw sensitive bodies**. |

**P2 / later feature structures from PRD Section 6**: `persona_observations`, `learning_candidates`, `discovery_results`, `insights_snapshots` and expanded historical retention/storage can be **documented as deferred** for later focused migrations. Do not generate untested empty tables solely to claim the full PRD is implemented. List each PRD entity with IMPLEMENTED / DEFERRED in the implementation PR. All P0/P1 prerequisite relations listed above must be testable now; if splitting reduces risk, propose a revised scope before making changes.

Minimum data-integrity rules:
- All account-scoped entities use an explicit account FK; use composite keys/FKs or equivalent constraints to prevent a proposal/job/approval referencing an event, proposal or persona owned by another account. Test negative inserts at the SQL layer.
- Uniqueness uses immutable provider IDs and scoped external keys; if two accounts have the same incoming external reply ID, they must still remain isolated; duplicate event within the same account must be rejected/deduplicated.
- One active persona binding per provider account; disabled/revoked operator/account or missing binding must fail closed on account-sensitive paths.
- Approved content, mode and account association cannot silently change after final operator approval. Edits require a new review step where applicable.
- Explicit foreign-key delete behavior; no cascading loss of audit/attempt evidence by accident. Define minimal retention/deletion hooks, leaving final user-data retention policy for owner decision.

## 5. Security / Supabase-specific requirements

- **Public repository:** no real connection strings, generated service keys, JWTs, credentials, .env or production snapshots in files, commits, Actions logs or Telegram. Use synthetic test data. `DATABASE_URL` is confidential; `SUPABASE_SECRET_KEY` is backend-only, never needed for basic local schema tests.
- Prefer least-privilege architecture; for tables in exposed `public` schema, **enable RLS on every table**, and explicitly restrict/revoke `anon`/`authenticated` access unless a justified product auth model exists. A backend-only PostBro Telegram application is **not** automatically using Supabase Auth; never create permissive `auth.uid()` policies without a matching identity model. A private schema can be proposed with documented pros/cons and restricted grants.
- Supabase `sb_secret_` server keys and legacy service-role credentials **bypass RLS**; operator-account authorization **must also be enforced and tested in backend service code**. An RLS-only test is insufficient, and service-key-only queries do not test RLS.
- Avoid publicly executable `SECURITY DEFINER` functions and permissive default grants; if absolutely needed for transaction safety, use a restricted non-exposed schema, restricted EXECUTE, fixed search_path, explicit identity checks and security tests. Prefer invoker rights where possible.
- Use parameterized SQL / safe DB driver APIs, explicit DB transactions and redacted, structured errors. No production database URL in CI.
- No elevated Supabase management PAT is required for this task; hosted project, region, secret API key and Storage bucket remain NOT_CONFIGURED until separately approved.

## 6. Concurrency, idempotency and safety tests

Implement DB-level operations and tests for:

1. **Idempotent event ingest:** repeating identical owned-reply provider ID within one account does not create two events; different accounts stay isolated.
2. **One-job-claim:** N concurrent workers claiming one due job yield exactly one valid lease/claim; lease token/owner prevents a stale worker from finalizing after takeover. Record attempt count and safe expiry/recovery.
3. **Ambiguous remote outcome:** `needs_reconciliation` remains terminal-to-auto-retry until explicit reconciler/manual intervention; NEVER blindly enqueue another reply on timeout. Do not claim exactly-once Meta delivery from DB guarantees alone.
4. **Approval compare-and-swap:** two simultaneous approvals/replay attempts result in one winning transition; expired/rejected/revoked action never authorizes send. An edit/regenerate invalidates the stale approval version.
5. **Cross-account denial:** operator A cannot query/mutate account B, nor attach B's persona/proposal/job to A. Test API/service and DB constraints as separate layers.
6. **OAuth replay foundation:** hashed one-time state consumed once, expires by time and bound to originating operator, without implementing live OAuth.
7. **Migration repeatability:** clean DB can apply versioned migrations and create representative rows with FK constraints; exercise teardown/reset and realistic seeded fixtures. Document whether rollback is destructive and **do not execute it against hosted data**.

The implementation PR must include exact test commands, measured results/exit codes, and a short explanation of which security guarantees remain unproven until a hosted Supabase project exists.

## 7. Implementation constraints / exclusions

- Do not call Meta, publish/reply to Threads, create PostBro Telegram bot, provision hosted Supabase, use the existing Hermes bot as product bot, configure DNS, deploy containers publicly or mutate any external account.
- Do not build product engagement execution workers yet: **DB claim primitives only**. Do not add Redis, Kafka, new microservices, Kubernetes or use Postiz.
- Do not implement real OAuth/token exchange, real token encryption algorithms or account connection UX; store ciphertext-capable schema/interface only. PB-P0-003 will implement actual encryption, key rotation and token lifecycle.
- Don't add AI persona learning, insights, discovery, external engagement, UI or broad storage/media workflows in this task.
- No production write/test, even if a Supabase connector is authenticated elsewhere. Explicit owner authorization is required per project and operation.
- Reuse existing strict TypeScript structure and tests. New deps only with justified maintained versions, lockfile and licensing review.
- Current Supabase behaviour, local CLI commands and RLS/Data API exposure should be rechecked against official docs when Hermes implements: Supabase changed default API exposure rules in 2026; never assume `public` tables are automatically accessible or safe.

## 8. Acceptance criteria (task-specific)

- **DB-01:** SQL migration(s) apply from a clean local Postgres DB using documented, repeatable commands; CI checks run DB tests and fail on migrations/tests breaking.
- **DB-02:** Schema has scoped identity, account/persona/proposal/job/approval/action/audit relations; all mandatory PK/FK/unique and per-account integrity verified by inserts/rejections.
- **DB-03:** Backend code demonstrates fail-closed operator/account access with test fixtures for two accounts and two operators, including absent/disabled/no-binding cases.
- **DB-04:** Approval CAS and concurrent job claims proven by real transactional Postgres tests, not mocks or a single happy-path request.
- **DB-05:** Duplicate incoming events and external action idempotency proven; ambiguity triggers needs_reconciliation without re-sending.
- **DB-06:** RLS/grants tested under a non-privileged context and shown deny-by-default where applicable; backend service authorization tested separately with elevated-server context.
- **DB-07:** Existing GET `/health` and previous 6 tests still pass without cloud secrets. A DB failure is observable and does not falsely mark connected service healthy.
- **DB-08:** No secret/production side effect; repo remains publicly safe; no Postiz or unnecessary runtime dependency; exact integration evidence and limitations supplied.
- **DB-09:** Docs/SETUP and env template updated only for genuinely implemented config; list non-implemented PRD entities and hosted-project blockers honestly.
- **DB-10:** GitHub feature branch PR with `POSTBRO_HANDOFF_V1`, passed required `lint-typecheck-test`, detailed test commands, risk/rollback notes; NO MERGE without owner approval.

**Definition of done:** DB-01..DB-10 verified for LOCAL foundation. Mark **HOSTED_SUPABASE_NOT_VERIFIED** until a dedicated/existing project, region, access and smoke tests are explicitly approved. A local PASS does not mean the app can operate on live Threads.
