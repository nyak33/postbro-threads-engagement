# PB-P0-002H — Hosted Supabase Readiness Hardening

**Status:** SPECIFICATION PROPOSED; implementation not started. This task must be reviewed/merged separately before Hermes receives an implementation kickoff. **No remote SQL/migration authorization.**
**Product authority:** [PRD](../PRD.md), [Architecture](../ARCHITECTURE.md), [Setup](../SETUP.md), [PB-P0-002](PB-P0-002.md), [Development Workflow](../DEVELOPMENT_WORKFLOW.md).
**Dependency:** PB-P0-002 local database foundation merged into main in PR #5 with 20/20 passing CI tests. Hosted Supabase dedicated project \`postbro-core\` exists in Singapore; database is PostgreSQL 17.11. Cloud access was assessed read-only on 2026-10-23.

## 1. Why this task exists

The approved PB-P0-002 scope stopped at **LOCAL database foundation**. A separate read-only audit against the newly created **hosted Supabase** project found that it can create roles and schemas and that the \`postbro\` schema, tables and custom roles do not exist yet. Existing Supabase Security Advisor reported no findings. This DOES NOT prove that the current SQL migration or application connection should be run as-is on the hosted database.

Four hardening workstreams must be resolved in a **reviewed feature PR before any hosted schema write**:

### H-01: Choose ONE migration-history authority and harden the runner

The repository includes \`src/db/migrate.ts\` and \`postbro.schema_migrations\`. Supabase CLI instead uses \`supabase_migrations.schema_migrations\`. Do NOT run both systems independently on a hosted database; they would not know which migrations the other applied.

- Document and implement the chosen **single** mechanism; if adopting Supabase CLI, ensure valid filename/version naming and do not leave the application runner in a state that could accidentally replay the same SQL. If retaining the application runner, define how Supabase CLI will be excluded and how history is backed up.
- Make repeated executions and **concurrent migration processes** safe: lock, transactional ledger check, crash recovery and explicit failure/no partial migration test.
- Ensure migration content has an immutable checksum or equivalent verified change-detection so edits to previously applied SQL do not silently succeed. Define migration version naming and execution order.
- No destructive rollback command or replay against a hosted project. Provide operator recovery/backups plan, plus a pre-apply dry run/diff and verification steps.
- Avoid broad changes to the already-merged local schema where a focused additive migration/runner patch is sufficient. Existing database is empty, but keep forward-migration discipline.

### H-02: Decide restricted runtime database identity

The migration creates \`postbro_app\` as **NOLOGIN**, designed for grants/RLS; production runtime currently has no separate login identity bound to this role.

- Propose a production-safe application login and narrow grants. Do not connect PostBro's persistent runtime as the \`postgres\` migration/admin role or use a bypass-RLS secret for ordinary account queries.
- Verify transaction-scoped \`postbro.operator_id\` / \`postbro.account_id\` are set by trusted server code, cannot be influenced by caller-provided identity, and are cleared/reset on pooled connections.
- Document how a dedicated login inherits/grants access to \`postbro_app\`, with **no passwords in Git, PR, logs, Telegram or AI context**. If provisioning roles requires remote SQL, implement only a reviewed, parameterized provisioning plan and tests against local PostgreSQL for now.
- Test least-privilege runtime account access, default-deny, cross-account denial, role escalation attempts, RLS and permission denial with nonprivileged credentials.
- Confirm schema \`postbro\` remains private and **not in exposed Supabase Data API schemas**; do not grant \`anon\` or \`authenticated\` access.

### H-03: TLS and network connection design

Supabase Free direct PostgreSQL endpoint commonly requires **IPv6**; Supavisor **session pooler** accepts IPv4. The target Contabo VPS's IPv6 egress has **not** been checked. The \`pg\` client in \`src/db/client.ts\` currently takes a generic connection string without a documented TLS verification policy.

- Prepare **read-only** VPS network check instructions; do not ask for remote credentials in chat.
- Select direct (if VPS IPv6 functional) or IPv4 Supavisor session pooler (port 5432) for persistent app traffic. Avoid transaction pooler for migration/session-sensitive operations; migrations should prefer direct when supported.
- Require encrypted TLS connection and correctly validated server identity/CA where supported; document cert handling, connection timeouts, max connections, credentials rotation and pool shutdown. Never force \`rejectUnauthorized:false\`.
- Add deterministic configuration validation/negative tests; no hosted DB password in CI or application logs.

### H-04: Rehearsal, deployment approval and verification boundary

- Reproduce database migration and least-privilege tests against a **fresh disposable PostgreSQL 17.11** environment, preserving the existing 20+ tests and required CI.
- Validate against official current Supabase role, RLS, connection, Data API and migration docs. Explicitly document the local-vs-hosted differences and what cannot be proven before a controlled hosted smoke test.
- A separate owner-approved deployment action will be required to actually apply the schema to the **dedicated PostBro cloud project**. Before doing so, record the exact intended project, approved migration SHA, backup/restore strategy, rollback limitations, deployment identity, run command, and post-apply read-only validation (tables, grants, RLS, indexes and role access).
- Do not attempt to create Storage bucket or Meta/TG credentials in this task. Do not run any hosted SQL, including an apparently harmless CREATE, GRANT, ALTER, migration or ad hoc seed. Read-only metadata checks were completed separately.
